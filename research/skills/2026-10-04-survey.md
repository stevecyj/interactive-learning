## 把靜態來源轉成動態畫面的思考方式

下面是本次歸納的工作方式，不是任何一份 Skill 的原文，也不是必須導入的新框架。

```mermaid
flowchart LR
  A[來源與 brief] --> B[這一步要回答的問題]
  B --> C[固定條件與可變輸入]
  C --> D[規則與中間狀態]
  D --> E[圖形／數值／文字對照]
  E --> F[預測與情境判斷]
  F --> C
```

每個互動先回答六件事：

| 要決定的事 | 白話問題 | 產出 |
|---|---|---|
| 教學問題 | 讀者現在看不懂的關係是什麼？ | 一句核心問題 |
| 狀態 | 哪些事實固定，哪些條件可改？ | 變數、範圍、預設值與單位 |
| 規則 | 變更如何影響中間步驟和結果？ | 可核對的運算、規則與適用情境 |
| 畫面映射 | 每個符號在圖上對應哪個東西？ | 原文／展開結構／圖／數值的對照 |
| 操作 | 讀者要做什麼才能看出差異？ | 一個有目的的 slider、step、選擇或拖曳 |
| 回饋 | 改完後該看哪裡、比對什麼？ | 改變標記、說明、反例與可重試的判斷 |

這個分解受到 [ViviDoc 的 SRTC 規格](https://aclanthology.org/2026.acl-demo.79.pdf)、[反應式文件](https://worrydream.com/ExplorableExplanations/)及 [PhET 設計原則](https://phet.colorado.edu/en/research/design-principles)啟發。來源能支持外部方法的描述；這裡的六欄組合與專案用法是本次建議。

重點是選擇能暴露關係的互動。讀者拖滑桿後若只能看到數字換掉，仍可能不知道原因；最好能看見哪個中間部分先改變，再看見結果如何跟著改變。動畫中的速度、位置與尺寸也要有意義：若只用來帶視線，應標為示意，避免被當成實際量測。

### 套到現有 CIDR 主題會長什麼樣

例子固定 `10.0.0.0` 為區塊起點，先只把前綴 `/24` 改成 `/25`。

| 同一份狀態的表示 | /24 | /25 | 畫面可如何指出原因 |
|---|---|---|---|
| 固定定義 | IPv4 共 32 位元 | IPv4 共 32 位元 | 32 格與「固定」標籤保留 |
| 可變輸入 | 網路前綴 24 位元 | 網路前綴 25 位元 | 分界線右移一格，標出新固定的位元 |
| 推導：主機位元 | `32−24=8` | `32−25=7` | 可自由變動的格子少一格 |
| 推導：總地址數 | `2^8=256` | `2^7=128` | 先展示少一格少掉一半組合，再顯示數字 |
| 地址範圍 | `10.0.0.0–10.0.0.255` | `10.0.0.0–10.0.0.127` | 同比例範圍條縮半；起點固定，終點改變 |
| 一般 AWS 子網情境 | 5 個地址保留；251 個可分配 | 5 個地址保留；123 個可分配 | 保留區段另加文字／紋理標記，不和 IPv4 定義混合 |

地址範圍與一般 AWS IPv4 子網的保留規則已對照 [AWS 官方文件](https://docs.aws.amazon.com/vpc/latest/userguide/subnet-sizing.html)；上表的主機位元與容量是算式推導。此例不涵蓋 BYOIP；官方文件另列其例外。AWS 子網允許的 IPv4 前綴是 `/16` 至 `/28`，不能把一般 CIDR `/31`、`/32` 的例子直接當成可建立的 AWS 子網。

可以先問：「前綴只多一位，為什麼地址數減半？」讓讀者預測後再操作。接著換一個候選 IP，要求用位元分界與範圍判斷。最後才加入 AWS 保留規則。這是後續實驗構想，尚未修改或測試現有教材。

## 哪類內容適合哪種動態呈現

這是選型表，不要求每份教材都做所有形式。

| 靜態內容的關係 | 適合的呈現 | 可加入的讀者操作 | 適合的例子／參考 |
|---|---|---|---|
| 組成、層級、包含 | 展開、剖面、由全局放大到局部 | 選一層、切換標籤、回到全圖 | VPC→Subnet→資源；[Bartosz：Engine](https://ciechanow.ski/internal-combustion-engine/) |
| 一個參數造成結果差異 | 參數與圖形、數字、文字同步 | 改一個條件、重設、保留 A/B 對照 | CIDR；[PhET](https://phet.colorado.edu/en/research/design-principles)、[Tangle](https://worrydream.com/Tangle/) |
| 有先後順序的運算 | 步進、目前步驟高亮、中間值表 | 上一步／下一步、預測下一步 | mask 比對、程式執行；[Python Tutor](https://pythontutor.com/) |
| 流動、等待、失敗、重試 | 流程圖中的 token／封包、時間軸 | 送請求、調延遲／失敗率、暫停 | [Queueing](https://encore.dev/blog/queueing)、[Retries](https://encore.dev/blog/retries) |
| 規則差異與取捨 | 同一輸入並排跑兩種方法 | 切換規則、同步比較、查看差值 | FIFO／LIFO、一般規則／服務規則 |
| 整體由個別資料形成 | 個別樣本逐步累積成分布或摘要 | 新增樣本、改門檻、看原資料 | [Seeing Theory](https://seeing-theory.brown.edu/)、[Observable](https://observablehq.github.io/documentation/notebooks/) |
| 原始寫法與展開結構 | 同一物件變形、位置對齊、分組展開 | 展開一部分、改輸入、回看原式 | 十進位→位元→分界；[Morph](https://support.microsoft.com/en-gb/powerpoint/morph-transition-tips-and-tricks) |
| 判斷與易混淆案例 | 先選答案，再逐步指出條件與規則 | 預測、分類、解釋、重試 | [teaching-explainer](https://github.com/rlfordon/teaching-explainer) |

公式、流程、層級與敘事需要的畫面不同。不能只因某個效果漂亮，就把所有內容套進同一種動畫。

## 從 PowerPoint 與動態簡報借用的方法

簡報的技巧值得納入，尤其能提供「同一個物件跨步驟仍看得出是誰」和「這一步該看哪裡」的做法。搬到網頁後，再接上可調參數與真實模型。

| 方法與原始來源 | 可借用的原理 | 搬到本專案的方式 |
|---|---|---|
| [PowerPoint Morph](https://support.microsoft.com/en-gb/powerpoint/morph-transition-tips-and-tricks) | 兩個狀態中對應同一物件，讓位置、尺寸或排列連續變化 | `/24`→`/25` 保留同一組位元格，只改分界與標記；可以回放兩種狀態 |
| [PowerPoint Zoom](https://support.microsoft.com/en-us/powerpoint/use-zoom-for-powerpoint-to-bring-your-presentation-to-life) | 從總覽進入局部，再回到總覽；可自行決定探索順序 | 由 VPC 全圖點入子網，回到全圖時保留當前選擇與比較結果 |
| [reveal.js Fragments](https://revealjs.com/fragments/) | 在同一畫面逐步揭露與強調，讓每次新增有明確順序 | 計算過程每次露出一個推導；先作答後才揭露解題步驟 |
| [reveal.js Auto-Animate](https://revealjs.com/auto-animate/) | 用共同身份匹配相鄰狀態的物件 | 保留圖的位置與物件，讓讀者辨認究竟改了什麼；原生 SVG／CSS 即可借用這個思路 |
| [reveal.js Code](https://revealjs.com/code/) | 分段高亮同一份程式碼 | 目前規則／程式行與圖中的資料變更同步，避免重新顯示整段而失去對照 |
| [frontend-slides](https://github.com/zarazhangrui/frontend-slides) | 導覽、進度、快捷鍵與風格探索 | 借導覽方法；保留本專案的手機重排需求 |

以上官方文件已閱讀；沒有製作 PPT 或安裝 reveal.js。簡報框架不是必要前提：若只需要這些局部效果，原生 HTML、SVG、CSS 與 JavaScript 可以實作。

另需把「展示過程」與「改條件做實驗」寫清楚。播放既定步驟能幫助看懂過程；讓讀者改值後重新計算，則能檢查不同情境。兩者可搭配，但不應把翻頁本身當成已完成理解型互動。

CIDR 前綴是整數。即使分界移動使用平滑轉場，也不能把 `/24.5` 顯示成有效網路參數；邏輯值仍應落在有效狀態。動畫要尊重內容的離散或連續性。

### 三個特別值得保留的發現

**1. `explorable-skills` 的互動原型清單。** 實際讀取 [SKILL.md](https://github.com/gmchande/explorable-skills/blob/main/skills/explorable/SKILL.md) 與 primitives。它把可調數字、步進、拖曳、圖層、時間軸、分支、預測揭曉等形式連到不同理解任務。最值得借的是「先說讀者會因操作理解什麼，再決定 widget」。人氣只有 4 stars，尚無充分社群或生成品質證據，適合抽方法做小實驗。

**2. `explain-this` 有來源 intake 與獨立事實核對。** [creating-explainers](https://github.com/analyticalmonk/explain-this/blob/main/skills/creating-explainers/SKILL.md) 將文件、研究與混合來源分開處理；[fact-checking](https://github.com/analyticalmonk/explain-this/blob/main/skills/fact-checking-explainers/SKILL.md) 要把可查主張對回支持它的來源。這比只生成視覺頁更貼近 references 的用途。但其固定 Canvas、文章骨架、outline 確認與外部字體，都需要依本專案需求調整。

**3. MicroSims 會先問「希望學習者做什麼」。** 目前 [generator](https://github.com/dmccreary/ibook-skills/blob/main/skills/microsim-generator/SKILL.md) 將學習動作與呈現形式連結，例如需要預測就用可停下來的步進，不能只是持續播放。這個選型方法值得借；完整教材庫工作流目前較重。舊 `claude-skills` repo 已轉向 `ibook-skills`，且 [舊 microsims 文件](https://dmccreary.github.io/claude-skills/skill-descriptions/microsims/)有歷史快照標記，不能把舊分類直接當現況。

## 後續如何投入 token 與時間

先保留這次的廣度，再用一個小而一致的任務比較。建議依下列順序做後續實驗，這次尚未執行。

1. **同一份 brief 與官方來源**：用目前 CIDR 的一個卡點做 2–3 種版本，例如位元分界、範圍圖與逐步運算。保持綠色風格，先比較理解方式。
2. **先寫一小段互動規格**：學習問題、固定／可變、畫面映射、操作、規則、預期觀察與反例；可直接放 brief，暫不需要建立完整 DocSpec 平台。
3. **對照兩種生成流程**：現有 prompt 與「來源核對＋互動規格＋局部 QA」流程。若之後試 Skill，先挑 `html-artifacts`、`teaching-explainer`、`html-explainer` 或 `explain-this` 中少數候選，避免同時堆疊全部規則。
4. **用相同檢查判斷成本與價值**：有無算錯、來源能否對回、操作能否看見原因、手機／鍵盤／離線是否通過、重做幾次、是否能處理新情境。星數只作閱讀排序的補充。
5. **再決定需不需要安裝**：如果少量可讀規則與原生 HTML 就足夠，留在共用 prompt 即可；大量重複產出、元件與 QA 確實節省時間時，才考慮做專案 Skill。

目前 prompt 已包含很多必要原則，不需要因這份 survey 立刻擴寫成很長的指令。最值得實驗的增量是「來源主張如何對到互動模型」和「同一張圖如何承載前後狀態」，而不是增加裝飾效果或先更換技術堆疊。
